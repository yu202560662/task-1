# Git 核心操作：Clone、Add、Commit、Push

## 1. 概述
 Git 版本控制的核心操作流程，重点围绕 `clone`、`add`、`commit`、`push` 四个基础命令的原理、操作规范及在 VSCode 中的实践应用展开。

## 2. 核心结论
Git 工作流本质是文件在四大分区（工作区、暂存区、本地仓库、远端仓库）间的同步过程。`clone` 用于拉取远端仓库并初始化本地环境；`add` 将改动移入暂存区作为提交前检查点；`commit` 生成状态快照存入本地仓库形成可回溯历史链；`push` 将本地提交同步至远端实现备份与协作。VSCode 等工具虽简化了操作，但理解底层原理仍是避免误操作的关键。




- Git 操作本质是文件在工作区、暂存区、本地仓库、远端仓库四个分区之间的同步流转。
- `git clone` 是获取远端仓库并创建本地存储库与工作目录的标准方式。
- `git add` 将文件移入暂存区（Staging Area），作为 commit 前的检查点；VSCode 默认 commit 时自动执行 add，但支持手动 stage 以实现选择性提交。
- `git commit` 保存仓库状态快照，形成可回溯的历史链；建议每完成一个功能点即做一次 commit。
- `git push` 将本地仓库改动推送至远端仓库，仅推送后的代码才对他人可见；需具备仓库管理员或协作者权限。
- `git pull` 等价于 `git fetch` + `git merge`，用于拉取远端最新改动并合并到本地。
- 绑定远端仓库有两种方式：克隆已有仓库，或本地初始化后通过 Publish 推送到新建远端仓库。



### 3.1 git clone：远端仓库克隆与本地初始化
- **背景信息**：在开始参与项目或获取他人代码时，需要将远端仓库（如 GitHub）完整拉取到本地，同时建立本地存储库与工作目录的对应关系。这是与远端协作的第一步。
- **核心要点**：
    - `git clone` 把远端仓库保存到本地，同时自动创建出本地存储库（Local Repository）和本地工作目录（Working Directory）。
    - 在 VSCode 中操作：Source Control 面板点击“克隆”按钮 → 粘贴仓库地址 → 选择本地存放文件夹 → 完成克隆。
    - 仓库地址结构为 `github.com/[开发者]/[仓库名]`，中间部分为开发者账号名，最后为仓库英文名。
    - 克隆后可直接在本地进行开发、修改、提交等操作，所有改动初始仅存在于本地。
    - 只有仓库管理员或被授权的协作者才能向该仓库 push 代码；非授权者需通过 Fork + PR 流程贡献代码。
- **结论**：`clone` 是获取远端仓库并建立本地开发环境的标准化入口，一步完成远端拉取与本地初始化。

### 3.2 git add：暂存区机制与选择性提交
- **背景信息**：Git 设计了暂存区（Staging Area / Index）作为 commit 前的检查点，允许开发者精确控制哪些改动进入下一次提交。虽然现代 IDE 淡化了这一概念，但理解其原理对精细化版本管理至关重要。
- **核心要点**：
    - 暂存区是 commit 之前的准备区域，使用 `git add` 将指定文件从工作区移入暂存区。
    - VSCode 默认行为：点击 Commit 按钮时自动执行 `git add`，将所有已修改文件一并提交，大幅简化操作复杂度。
    - VSCode 手动 Stage：在文件右侧点击 “+” 号（Stage Changes），可将单个文件添加到暂存区；此时 commit 仅提交暂存区内的文件，未 stage 的文件不会被包含。
    - 若不手动 stage，VSCode 默认将所有修改文件一起 commit。
    - 暂存区的核心价值在于实现“选择性提交”，例如只提交已完成的功能文件，而将未完成或调试中的文件排除在外。
- **结论**：`add` 是连接工作区与本地仓库的桥梁，暂存区机制使开发者能够精确控制每次提交的内容粒度，VSCode 提供了自动化与手动两种模式以适应不同场景。

### 3.3 git commit：状态快照与历史链构建
- **背景信息**：commit 是 Git 版本控制的核心单元，每一次 commit 都记录了仓库在某一时刻的完整状态。良好的 commit 习惯是代码可追溯、可回退、可协作的基础。
- **核心要点**：
    - 每次 commit 保存仓库此时的状态快照，所有文件状态均被记录；随着 commit 增多，形成一条可回溯的历史链。
    - 每个参与者的每次改动都会被 commit 链路完整记录，便于审计与问题定位。
    - VSCode 操作：Source Control 面板填写 commit message（提交摘要，讲清本次改动内容）→ 点击 Commit 按钮完成提交。
    - 最佳实践：每让 AI 完成一个小的功能点就做一次 commit，以便在 AI 改动不符合预期时随时 discard 回退，再调整提示词重做。
    - Commit ID 分为长 ID 与短 ID（前7位），两者功能等价且在仓库内绝对唯一；与 AI 交流时应使用 commit ID 精确定位，如“把仓库还原到 [commit ID] 状态”。
    - 三种回退机制与 commit 的关系：
        - **discard**：放弃未 commit 的更改，适用于文件修改尚未提交的场景。
        - **reset**：强制回退到指定历史状态，仅适用于单人分支或未推送远端的改动；多人协作分支禁止使用。
        - **revert**：生成反向提交抵消目标 commit，安全适用于多人协作分支。
- **结论**：`commit` 是构建版本历史的原子操作，高频、小粒度的 commit 配合清晰的 message 和 ID 引用，是实现安全回退与高效 AI 协作的前提。

### 3.4 git push：远端同步与权限约束
- **背景信息**：本地 commit 仅存在于个人机器上，只有通过 push 将改动推送至远端仓库，才能实现代码备份、团队共享与协作开发。push 操作涉及权限校验与同步策略，是多人协作中最需谨慎的环节。
- **核心要点**：
    - `git push` 将本地仓库的改动推送到远端存储库（Remote Repository），只有 push 后的代码才对他人可见。
    - 权限约束：只有仓库管理员或被添加的协作者才能成功 push；非授权者 push 会被拒绝，需通过 Fork + PR 流程贡献代码。
    - 同步状态标识：VSCode 中 origin/main 与 main 处于同一提交时表示同步完成；若本地有未推送提交，Sync Changes 按钮显示上箭头；若远端有新提交，显示下箭头。
    - `git pull` 等价于 `git fetch` + `git merge`，用于拉取远端最新改动并合并到本地；VSCode 中 Sync Changes 按钮一键完成 pull 与 push。
    - 绑定远端仓库的两种方式：
        - 克隆已有远端仓库到本地（`git clone`）。
        - 本地初始化仓库后，通过 Publish 按钮推送到新建的远端仓库（可选公开/私有）。
    - 强制推送（`git push -f`）仅在 rebase 变基后必须使用，且**严禁在多人协作分支上使用**，否则可能覆盖他人代码。
- **结论**：`push` 是本地改动进入团队协作体系的最终出口，必须严格遵守权限规则与同步流程；普通 push 用于日常同步，强制推送仅限个人分支的变基场景。
